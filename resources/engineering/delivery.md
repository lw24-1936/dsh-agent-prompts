# 交付、PR 与提交

## 1. 交付状态分开记

不要用“做完了”一句话。逐项：

| 项 | 状态 | 证据 |
|---|---|---|
| 实现 | 完成/部分/未做 | 文件/commit |
| 编译 | 通过/失败/未跑 | 命令 |
| 测试编译 | 通过/失败/未跑 | 命令 |
| 单元/切片 | 通过/失败/跳过 | 用例/报告 |
| E2E/冒烟 | 通过/失败/未跑 | 环境/截图 |
| 审查 | 通过/有未关闭发现 | 发现 ID |
| 提交 | 已提交/未提交 | hash |
| 推送 | 已推送/未推送 | 远端/分支 |
| 部署 | 已部署/未部署 | 环境/版本 |
| 现场验收 | 通过/未做 | 用户确认 |

“测试通过”不等于“已推送/已部署/业务验收”。

## 2. 交付前检查

- 需求验收逐项有当前候选证据；保持项有回归。
- 没有未关闭 P0/P1 发现；P2 有记录/排期。
- 工作区没有无关改动/临时文件/密钥/大产物。
- 迁移/配置/依赖变更可回滚或可重放。
- 文档/README/CHANGELOG 按项目要求更新。
- 失败/未验证项明确写出，不藏在“其他都通过”后面。

## 3. 提交

- 一个提交一个逻辑变更；能独立构建/回滚。
- Conventional Commits：`feat(scope): ...`、`fix(scope): ...`、`refactor: ...`、`docs: ...`、`test: ...`、`chore: ...`。
- 标题小写、祈使、无句号、约 70 字符内；scope 是模块/包/功能。
- 不把无关修复/依赖升级/顺手重构混进同一提交。
- 已推送且正在 review 的提交不改写；追加修复提交。
- 不提交 `.env`/密钥/本地绝对路径/大二进制/生成物（按项目规则）。

## 4. PR / 变更说明

说明“改了什么行为、为什么”，不是文件清单。按变更大小决定篇幅：

```md
## 目标
## 变更
## 验证
- 命令：
- 结果：
## 影响/风险
## 截图（UI 改动）
## 未验证/未做
```

规则：

- 写明 base...head 范围；堆叠分支只描述本 PR 自己的变更。
- 验证写命令 + 结果 + 环境；不是“已测试”。
- UI 改动附改前/改后截图或录屏；四个视口至少关键页。
- 架构/性能/兼容性声明要有文件/符号/数据依据。
- 未验证、跳过、环境限制明确写；不要把“预计”写成“已验证”。

## 5. CI / 合并

- 推送后看 CI；失败先读日志定位，修根因再推。
- 最多 3 轮修复；flaky/无关/需要权限时停止并报告，不反复重跑掩盖。
- 不为了绿禁用/跳过/弱化测试或 lint。
- 合并前确认 base 最新、冲突已解、review 意见已处理。
- 需要发布/部署时，按项目授权单独执行；PR 合并不等于发布。

## 6. 恢复点

中断/失败时留下：

- 当前候选（commit/diff/分支）
- 已完成/未完成项
- 最早失败点（环境/编译/测试/审查/部署）
- 已执行副作用（推送/部署/迁移/消息）
- 恢复命令/前提/禁止重放的动作

未知副作用先查状态，不重放。

## 7. 自检

- [ ] 交付状态逐项有证据，未验证项明确。
- [ ] 提交原子、消息规范、无无关改动/密钥。
- [ ] PR 说明有目标/验证/风险/截图/未做。
- [ ] CI 真实通过；没有禁用测试/弱化门禁。
- [ ] 恢复点/未完成项可交接。
