# 全栈问题排查规范（单体版）

> 本规范的第一原则：**先复现，再定位；先证据，后结论**。
> 没有证据的结论不写进报告，宁可写「未确认」。

## 一、开工前置

1. **环境信息已填**：服务地址、MySQL/Redis 连接、日志路径、可测账号。
2. **排查边界已确认**：允许哪些操作（只读 / 可改 / 可重启）、禁止哪些操作、时间窗口、影响范围。
3. **现象可描述**：报错原文、发生时间、影响范围、复现步骤、环境（dev/test/pre/pro）。

信息不全就**先提问，不要凭猜测开始**。

## 二、硬约束（不可违反）

1. **每次只改一处**，改完立即验证；一次改多处 = 无法归因。
2. **改必留痕**：所有改动追加进 `docs/DEV.md` 的「问题排查记录」。
3. **不删日志**、不清缓存、不重建表来"让问题消失"。
4. **不动生产数据**；确需动先备份并取得用户明确同意。
5. **不改与问题无关的代码**；顺手重构一律拒绝。
6. **不下无证据的结论**；推断必须标「推断」。
7. 生产环境优先只读排查；需要重启或改配置时先说明影响再执行。

## 三、排查流程（按序）

### 步骤 1：复现并固化

- 用最小路径复现；记录精确输入、时间点、traceId。
- 复现不了 → 先补齐观测（加日志 / 抓请求），**不要猜**。

### 步骤 2：定位到层

按「前端 → 网络 → 网关/入口 → 应用 → 数据层 → 中间件」逐层排除，一次只排除一层。
每层给出判定依据：是**该层报错**，还是**该层正常但上游异常**。

### 步骤 3：读日志找第一现场

- 从 **traceId** 入手，把一条请求的完整链路捞出来。
- 找**最早出现的异常**，不是最后那个异常。
- 区分：业务异常（预期内，`warn`）与系统异常（非预期，`error` + 堆栈）。

### 步骤 4：形成假设并验证

- 一次只提一个假设，写出「如果 A 成立，应该观察到 B」。
- 用日志 / SQL / 断点 / 复现去验证 B。
- 验证不成立就换假设，**不要修改假设去迁就现象**。

### 步骤 5：修复

- 最小改动，只动根因处。
- 修复必须能被验证：给出复现步骤 + 期望结果。
- 修完回归相邻功能，确认没有连带影响。

### 步骤 6：留痕

写入 `docs/DEV.md`「问题排查记录」，格式见下。

## 四、分层检查清单

| 层 | 先看什么 |
|---|---|
| 前端 | 控制台报错、Network 里请求是否发出、响应体与状态码、请求头 token |
| 网络/入口 | 是否到得了后端（URL、端口、跨域、反代）、Nginx/网关日志 |
| 应用 | 异常堆栈、业务分支、参数校验、事务边界、线程池 |
| 数据层 | 实际执行的 SQL 与参数、索引命中、锁等待、连接池占用 |
| 中间件 | Redis 连通与命中、MQ 堆积与死信、ES 查询与 mapping |

**连接类问题先验证连通性再查代码**：`telnet`/`nc` 端口、连接串、账号权限、库是否存在。

## 五、常见问题速查

| 现象 | 优先怀疑 |
|---|---|
| 接口 401 | token 缺失/过期、请求头名不对、拦截器顺序 |
| 接口 403 | 权限标识未注册、角色未授权、注解写错 |
| 接口 404 | 路径前缀、ContextPath、方法不匹配（GET/POST） |
| 500 且有堆栈 | 空指针、越界、类型转换、事务回滚 |
| 500 且无堆栈 | 被全局异常处理器吞了 → 查 handler 是否漏打日志 |
| 查询慢 | 缺索引、深分页、N+1、大事务 |
| 连接池耗尽 | 长事务、连接未释放、`maximum-pool-size` 过小 |
| 数据不一致 | 事务未覆盖、并发无锁、缓存与库双写 |
| 时区错乱 | 连接串缺 `serverTimezone`、序列化格式不统一 |
| 中文乱码 | 库/表字符集、连接串 `characterEncoding`、响应头 |

## 六、修复规范

1. 先写清「根因一句话」，再动手。
2. 改动范围最小；不引入新依赖（确需引入先问用户）。
3. 修完给出：根因 / 改了什么 / 为什么这样改 / 怎么验证 / 有无副作用。
4. 涉及数据修复时，给出可回滚的 SQL 与备份步骤。

## 七、排查记录格式（写入 `docs/DEV.md`）

```md
## 问题排查记录

### YYYY-MM-DD <一句话标题>
- 现象：
- 影响范围：
- 复现步骤：
- 定位过程：（逐层排除的关键证据）
- 根因：
- 修复：
- 验证：
- 遗留：
```

## 八、输出格式（每次回复固定）

1. `【现象确认】`
2. `【已排除】`（列出排除的层与依据）
3. `【当前假设】`
4. `【需要的证据 / 下一步】`
5. `【结论】`（有证据才写；无则写「未确认」）
6. `【修复方案】`（含验证方法）

## 九、必须停下来提问

- 排查边界未确认
- 环境信息缺失，无法复现
- 需要动生产数据 / 重启服务 / 改配置
- 根因指向设计缺陷（记录并建议转开发流程，不擅自重构）
- 同一现象有多种可能且无法用现有观测区分

## 十、绝对禁止

- 未复现就下结论
- 一次改多处
- 删除或清空日志、清理证据
- 用「重启试试」代替定位（可以重启，但必须先说明为什么重启、重启后看什么）
- 直接操作生产数据库
- 把「改完不报错了」当作根因已解决（要看是否真的命中根因）
