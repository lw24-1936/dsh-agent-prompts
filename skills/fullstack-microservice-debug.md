# 全栈问题排查规范（微服务版）

> 与单体版同一纪律：**先复现，再定位；先证据，后结论**。
> 本文件只补微服务特有的排查路径与故障模式；通用纪律见 `fullstack-monolith-debug`。
>
> **修复代码时同样受规约约束**：Java 遵循 `alibaba-java-standards`，前端遵循 `f2e-spec`；降级/熔断代码里尤其不能吞异常、不能用「返回 null」掩盖下游失败。

## 一、开工前置

1. 环境信息：网关地址、Nacos 地址与命名空间、各服务端口、日志目录、可测账号。
2. 排查边界：允许重启哪个服务、能不能动 Nacos 配置、能不能清 Sentinel 规则。
3. 现象：报错原文、traceId、涉及哪几个服务、影响范围。

## 二、硬约束

沿用单体版七条：一次只改一处、改必留痕、不删日志、不动生产数据、不顺手重构、不下无证据结论、生产优先只读。

**额外两条**：

8. **不擅自改 Nacos 配置**（会影响所有实例）；要改先说明影响面。
9. **不擅自扩容/重启整个服务组**；先用单个实例验证。

## 三、排查顺序（微服务专用）

```
前端 → 网关 → 服务注册(Nacos) → 目标服务 → 下游服务 → 中间件 → 数据层
```

关键：**先确认"请求到了哪个服务"，再查那个服务内部的逻辑**。微服务里最常见的浪费是：在前端调了半天，其实请求根本没出网关。

### 步骤 1：确认请求走到了哪里

- 网关日志：有没有这条 traceId？路由匹配到哪个服务？状态码？
- 没到网关 → 前端/网络/跨域问题。
- 到网关但 404 → 路由配置（Nacos 动态路由是否生效）。
- 到网关但 401/403 → 认证过滤器 / token / 权限标识。
- 到网关且转发 → 进下一步。

### 步骤 2：确认目标服务在线

- Nacos 控制台：服务列表里有没有这个实例？健康状态？IP 与端口对不对？
- 没有实例 → 服务启动失败或注册失败（看服务启动日志第一屏）。

### 步骤 3：串全链路

用**同一个 traceId** 在网关 + A 服务 + B 服务的日志里搜，确认断在哪一跳。
链路断了（下游没收到）→ 看 Feign 调用日志、超时、熔断。
链路没断但结果错 → 看业务逻辑与数据。

### 步骤 4：逐个中间件排除

Redis 连通 → MQ 是否堆积/死信 → Seata 事务状态 → ES 查询。

## 四、微服务故障速查

| 现象 | 优先怀疑 | 验证方式 |
|---|---|---|
| 网关 404 | 路由未加载、路径不匹配、`discovery.locator` 被关但没配路由 | 查 Nacos 里网关的 route 配置；网关日志打印匹配结果 |
| 网关 401 | token 未透传、认证过滤器顺序、白名单缺失 | 网关日志看请求头有没有 token |
| 服务注册不上 | Nacos 地址/命名空间/分组不对、网络不通、服务名与配置不一致 | Nacos 控制台 + 启动日志的注册结果 |
| Feign 404 | `@FeignClient` 的 `path` 与服务实际路径不一致、少了 context-path | 对比 Feign 声明与下游 `@RequestMapping` |
| Feign 超时 | 下游慢、连接池小、默认超时太短 | 下游日志耗时；调 `connectTimeout`/`readTimeout` 前先定位慢在哪 |
| Feign 报 fallback | 下游异常被兜底吞了 | **先看 fallbackFactory 里有没有把原始异常打出来**，否则根因丢失 |
| 熔断打开 | 错误率超阈值、并发超限 | Sentinel 控制台看规则与实时指标；确认是不是被自己的限流打中 |
| 分布式事务不回滚 | Seata 未生效、`@GlobalTransactional` 加错层、undo_log 表缺失 | 查 Seata 日志、每个库有没有 `undo_log` |
| MQ 堆积 | 消费慢/异常、prefetch 过大、消费者没起 | 队列深度、消费者数量、消费日志 |
| MQ 重复消费 | 未做幂等 | 查消息 ID 与业务去重逻辑 |
| 配置不生效 | Nacos 配置未发布、`spring.config.import` 缺、本地配置覆盖 | 启动日志打印的实际配置；`/actuator/env`（仅 dev） |
| 某服务内存/CPU 飙高 | 线程池打满、死循环、大对象 | `jstack` / `jmap`，看线程栈最多次数的调用 |
| 时好时坏 | 多实例配置不一致（某台是旧配置/旧版本） | 逐实例对比版本号与配置 |

## 五、日志与链路分析

1. **traceId 是主轴**：一条请求的全部日志应该能用一个 traceId 串起来；串不起来本身就是 bug（MDC 没透传）。
2. 看**最早**的异常，不看最后一个。
3. 跨服务时确认 traceId 是否通过请求头传下去了（`X-Trace-Id` 之类的头有没有出现在下游日志）。
4. 业务异常（预期内，`warn`）与系统异常（`error` + 堆栈）分开统计。

## 六、修复规范

1. 先写「根因一句话 + 影响哪几个服务」。
2. 改动最小；需要改公共模块（`common` / `api`）时，说明影响范围与回归清单。
3. 改配置类修复必须给出：改哪个 dataId、哪个 namespace、是否需要重启、灰度方式。
4. 修完给出：根因 / 改动 / 验证 / 副作用 / 需要回归的服务列表。
5. **修复不得新增 P0 反例**；改完跑 `node "<资源目录>/scan-redlines.mjs" --profile java --root .`，退出码必须为 0。
6. **fallback 不得吞异常**：必须记录原始异常与 traceId；不能用返回 null / 空对象掩盖故障（集合用空集合并记录日志）。

## 七、排查记录格式（写入 `docs/DEV.md`）

```md
## 问题排查记录

### YYYY-MM-DD <一句话标题>
- 现象：
- 涉及服务：
- traceId：
- 复现步骤：
- 定位过程：（网关 → 服务 → 下游，逐跳证据）
- 根因：
- 修复：（代码 / 配置 / 中间件）
- 验证：
- 遗留：
```

## 八、输出格式（固定）

1. `【现象确认】`
2. `【请求路径】`（前端 → 网关 → 服务 A → 服务 B）
3. `【已排除】`
4. `【当前假设】`
5. `【需要的证据 / 下一步】`
6. `【结论】`（无证据写「未确认」）
7. `【修复方案】`

## 九、必须停下来提问

- 排查边界未确认（尤其是否允许改 Nacos）
- 涉及分布式事务但不知道业务容忍度
- 需要重启多个服务或整个服务组
- 需要动生产数据或清 MQ
- 根因指向服务拆分/接口契约设计问题（记录，建议转开发流程）

## 十、绝对禁止

- 未确认请求走到哪个服务就开始改代码
- 用「重启一下看看」代替定位
- 改 Nacos 配置不说明影响面
- 清空 MQ 队列、删日志、清缓存来"消除现象"
- 在 fallback 里吞掉异常还不打日志
- 把「不报错了」当作根因已解决
